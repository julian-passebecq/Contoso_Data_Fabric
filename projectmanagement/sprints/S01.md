# S01 — Trustworthy local execution and orchestration

State: READY_FOR_DEV. Approved by tech lead on 2026-09-08.

Outcome: a locally provable foundation for long Fabric runs. A successful generation
has a stable identity; failures cannot masquerade as successful data; orchestration can
be exercised without a tenant; effects, timeouts and partial completion are diagnosable.

Scope: F00–F08, plus bounded F24 investigation and local-input provenance from F25.
Preserve existing application behavior except for the deliberate safety/validation
changes in ARCHITECTURE.md. Current baseline is a dirty checkout at 47a65b7; include its
stabilization changes in the candidate and later review. See REGISTERS.md before Git work.

Four development passes run consecutively. They are internal milestones, not user gates.
Do not add a new feature just to fill a pass. If a pass has an architecture blocker,
checkpoint it, complete independent approved work, and send one consolidated escalation.

## P1 — Stable generation and project contracts

Work primarily in Core generation/models/planning/projects and focused tests.

1. Capture branch/HEAD/dirty scope and reproduce the current local build/test baseline.
   Read the inherited logger/adapter/receipt fixes; retain their success/failure guarantees.
2. Implement ADR-001 dataset directories, metadata, inventory/digests, descriptor validation
   and atomic current-dataset publication. Add a generation result carrying the descriptor
   so downstream code can use the exact output of the run. Update call sites compatibly.
3. Preserve prior committed output after a failed/cancelled new generation. Test the point
   immediately before committing metadata with a controllable generator seam. No pointer
   may name a partial dataset. Reconcile the manifest actual counters with Parquet metadata
   in the real smoke path. Validate inventory for all three advertised formats using fixtures.
4. Validate all project enums and required nested objects before effects. Verify the existing
   JSON examples load. Keep actual vs requested orders and effective vs requested seed clear
   in UI/docs; remove claims that OrdersOverride guarantees an exact generated count.
5. Reproduce F24 with small inputs or isolated arithmetic tests. Do not silently change the
   original key-generation algorithm. If accepted planner values produce invalid output,
   propose a concrete supported bound or engine repair to the lead, with failing evidence.

Milestone M1: successful datasets are immutable, identifiable and validated; failures and
queued/active cancellation leave no falsely successful dataset; old project files work.
Developer gate: T01–T05 automated portions and existing lifetime/manifest/project tests.

## P2 — Testable and bounded orchestration

Work primarily in Fabric pipeline/API/OneLake composition and test fakes.

1. Introduce the narrow effect seams in ADR-002. Keep WPF using the production defaults.
   Route full-run uploads through the descriptor returned by generation. Bronze-start
   validates/resolves once; legacy/manual fallback follows ADR-001. Raw upload checks
   completeness before creating any remote item or uploading its first file.
2. Implement unique name/type resolution for Lakehouses/notebooks as well as model/report
   lookup, including delayed post-create visibility. Reject duplicates before mutations.
3. Add injectable HTTP/credentials/time to both API clients. Enforce finite request and
   operation bounds including authentication/delays. Test response codes, 429 exhaustion,
   Retry-After seconds/date, failures, unknown statuses, cancellation and lost responses.
   Verify current official Microsoft contracts before changing endpoint/status semantics;
   record those links in the development handoff. No cloud calls are needed for these tests.
4. Refuse foreign authenticated continuation/job URLs and pagination loops. Preserve
   cancellation in preflight. Do not retry uncertain mutation outcomes automatically.
5. Exercise all 21 valid contiguous stage ranges with fake effects. Prove selected order,
   dependency reads, no writes outside range, and no downstream calls after each failed or
   cancelled stage. Prepare is a separate action whose existing deferred-BI rule must hold.

Milestone M2: execution behavior and transport failure paths are observable and bounded
without credentials or real waits. Developer gate: T06–T08, full fast suite.

## P3 — Durable receipts and desktop behavior

Work primarily in PipelineRunReceipt, orchestration event emission and WPF handlers.

1. Implement ADR-003 snapshots and safe failure contract. Capture partial item provisioning
   immediately, and job identifiers as soon as available, including failing/current jobs.
   Store stage/notebook identity with each job. Version the receipt and keep old receipts
   readable or explicitly documented as historical, never falsely “recovered.”
2. Wrap Generate, Run, Prepare and Upload in one action receipt policy without nesting a
   receipt for every internal call. Generate and Run retain their public receipt-path behavior.
3. Serialize checkpoint writes and drain them before final status. Test interruption after
   completed effect, write failures, late progress, sanitization, and retention of partial IDs.
4. Keep desktop handlers thin and UI responsive. Make cancellation state consistent across
   progress, status, receipt and controls. Tell the user when an engine is draining or a
   remote job may still be running. Capture project settings once for each active action.

Milestone M3: the last durable receipt explains actual effects even after an incomplete
run; all four actions follow the same contract. Developer gate: T09–T11 automated portions.

## P4 — Integrate, exercise, and hand off

1. Add a repository-owned smoke harness/script under `scripts/verification/` (create it),
   with a documented exact command. It uses isolated output, explicit cache location and
   real Tiny/one-year/Parquet generation twice in one process; checks truth counts against
   orders/orderrows Parquet row metadata; validates descriptors, receipts and repeatability
   at the documented count level. The prior temporary harness is reference, not a dependency.
2. Add offline fixtures for CSV and Delta inventory, tampered data, legacy fallback, and
   failure/cancellation. Slow generation stays an explicit smoke command; fast CI tests
   must not download reference data. Record any smoke reference/network prerequisite.
3. Extend existing CI triggers so future `codex/**` sprint branches and new verification
   sources receive appropriate build/test coverage. Preserve PR coverage. Run the full
   solution Release build and fast suite. Do not report a local workflow edit as a CI run.
4. Execute the real smoke. Perform WPF checks if the environment supports interaction;
   otherwise give the tester a precise manual script and mark that evidence missing.
5. Update affected user documentation, add no obsolete count promises, and complete the
   developer handoff. Map every changed behavior to test IDs and every limitation to a
   backlog item. Record candidate revision plus hashes if dirty. Change status to
   READY_FOR_LIGHT_TEST only after development and required developer checks finish.

Milestone M4: one reviewable candidate, repeatable commands, consolidated limitations and
one handoff to light testing. Developer does not begin S02 while awaiting independent review.
